# Cluster ids match supercluster's encoding (offset = full input count)

Internal cluster ids are encoded to be **numerically interchangeable** with JS supercluster's: `cluster_id = points_len + (origin_index << 5) + (zoom + 1)`, where `points_len` is the **full input feature count** (including `geometry: null` features), matching supercluster's `this.points.length`. This overrides spec line 54, which says ids "are not required to match supercluster's `(i<<5)+zoom+len` encoding, since the oracle compares membership, not id values."

The override is forced by ticket 05's acceptance contract: `refs/supercluster/test/test.js` passes **literal JS cluster ids** as direct arguments — `getChildren(164)`, `getClusterExpansionZoom(4134)`, `getLeaves(165, 1, 6)` — and deep-equals the results against JS's expected outputs. With the spec's "need not match" permission taken literally, Rust ids diverged from JS by exactly the null-geometry count (places.json: Rust id 163 ↔ JS id 164 for the same cluster), so the test.js literals resolved to the wrong cluster on the Rust side. The acceptance criterion ("Verified behaviorally against test.js expected outputs") cannot pass without either an id-translation shim in the tests or matching JS's encoding — and matching the encoding is the cheaper, lower-surface choice (no translation layer, and the 04 membership oracle compares source-id multisets, not cluster ids, so it stays green regardless).

The change is a one-line value swap in `load` (`points_len = points.len()` instead of `coords.len()`); the `encode`/`decode` functions already took `points_len` as a parameter and are unchanged. Source ids stay geometry-bearing indices `[0, geom_bearing)`, which remain `< full_count` (since `geom_bearing <= full_count`), so the disjointness invariant (cluster ids ≥ `points_len`, source ids `< points_len`) holds — in fact more strongly.

## Considered Options

- **Match JS encoding (offset = full input count)** — chosen. Makes test.js literal ids work as direct arguments with no translation layer; the 04 oracle is id-agnostic so it stays green. Explicitly authorized by Ricky ("按照你推荐的方案来" in response to the recommended id-alignment option, plan approved via ExitPlanMode). This is, strictly, "compatibility code" under global CLAUDE.md rule #3; the authorization satisfies that rule.
- **Keep the geometry-bearing offset + id-translation shim in tests** — the spec's "need not match" permission, taken literally. Keeps the release lib free of any JS-encoding concern, but adds a translation surface to the tests and means Rust ids are not directly comparable to JS ids in any future cross-side debugging. Rejected because the acceptance contract uses literal ids, so a shim is unavoidable either way — and a shim in the tests is a worse place for the divergence than a documented encoding match.
