# Hybrid ids+encoded decode for `getClustersIds` (Point rows id-only, Cluster rows encoded)

`getClustersIds(bbox, zoom)` returns a **hybrid** shape: Point rows are a compact `Uint32Array` of source-feature ids (the main thread indexes its own already-held source features by id — zero per-row encode, zero JS object reconstruction), and Cluster rows are an encoded `Float64Array` pair (`cluster_rows` stride 5 + `cluster_aggregated` stride `specLen`) decoded via the existing `decodeQueryResult`. The main-thread `getClustersIds` performs hybrid decode and returns a `Feature[]` whose shape matches `getClusters` exactly — a drop-in replacement. The fully-encoded `getClusters` path is retained for the worker-wired decode case where the main thread holds no source features (e.g. `load_coords` input).

## Context

The ticket-09 attribution baseline established that on Point-dense viewports at 6M, the **main-thread decode** is the dominant per-query worker-wired tax (0.1216–0.1302 ms/q) — not the IPC floor, not the result-buffer copy. The encoded `getClusters` decode reads 5 Float64Array values per Point row (lng/lat/id/num_points/tag) even though the main thread already holds the identical source feature and pushes it by reference (`sourceFeatures[id]`, no allocation). `getClustersIds` exists (built in ticket 08, 9× the JS baseline on the FFI-direct column) but returned ids-only — unusable for rendering, since Clusters are synthesized inside WASM with no main-thread source feature, and a two-call API (ids for points, `getClusters` for clusters) is convoluted. The hybrid shape makes the ids path render-complete while *attempting* to bypass the per-Point typed-array read for the Point rows that dominate genuinely-Point-dense viewports.

**Measurement outcome (recorded in the ticket-10 Answer):** the **full worker-wired round-trip** (the direct before/after a consumer pays — FFI + copy + transfer + post-back, measured end-to-end) shows the hybrid path **wins at the 6M target scale**: uniform cluster-dense +62%, uniform point-dense +20.5%, clustered point-dense +9.5% (clustered cluster-dense ~flat, 36 results, sub-noise). At 1M the deltas are small in absolute terms (0.0065–0.018 ms/q) and mixed in sign — noise-dominated at that scale. The **decode-layer** attribution in isolation is noisy (the encoded-path decode measurement itself varied 2× between runs at 6M point-dense) and shouldn't be over-interpreted; the full-round-trip is the trustworthy signal. The decision stands on both architectural grounds (render-complete, drop-in, reuses the encoder) and the 6M measurement.

## Decision

- **Point rows → id-only `Uint32Array`.** The main thread already holds `sourceFeatures` (the geometry-bearing subset, indexed by feature_id — see `js/index.js`'s `load`). `decodeHybridResult` pushes `sourceFeatures[point_id]` directly — a reference push, zero allocation, and one Uint32Array read instead of the encoded path's five Float64Array reads per Point row. This is the win the ids path targets (its magnitude depends on how Point-dense the viewport truly is — see the Answer).
- **Cluster rows → encoded `Float64Array` pair, decoded via the existing `decodeQueryResult`.** Clusters are synthesized inside WASM (their lng/lat/num_points/aggregated are computed during the lattice scan, not held on the main thread), so their values must cross the boundary encoded — unavoidable. Reusing `encode_results` + `decodeQueryResult` verbatim means the cluster side is not a new code path: it is the existing encoded path, restricted to the cluster rows. The hybrid path is an **output-format change, not an algorithm change** — the lattice scan and `feature_at` are unchanged; only the FFI return shape differs.
- **Return contract:** `{ point_ids: Uint32Array, cluster_rows: Float64Array, cluster_aggregated: Float64Array, count, specLen }`. Two cluster buffers (rows + aggregated) mirror `getClusters`'s `{rows, aggregated}` so `decodeQueryResult` is reused without modification. (The ticket spec's `{point_ids, cluster_rows, count, specLen}` shorthand elided the aggregated buffer; Ricky approved the two-cluster-buffer layout — see the ticket-10 design question.)
- **`getClusters` (fully-encoded) retained unchanged.** The hybrid path requires the main thread to hold source features (GeoJSON `load`, not `load_coords`). When no source features are held, Point rows fall back to null-geometry Features — `getClusters` is the correct path for that case. Both paths ship; callers pick by input shape.

## Why

- **Why not pure ids (the ticket-08 shape)?** Pure ids cannot render Clusters — a Cluster has no source feature on the main thread, so its lng/lat/num_points/aggregated must cross encoded. A two-call API (ids for points + `getClusters` for clusters) is convoluted and doubles the IPC tax on mixed viewports. The hybrid shape is render-complete in one call.
- **Why not fully-encoded (keep `getClusters` only)?** The decode-layer attribution (ticket 09) showed decode is the dominant tax on Point-dense viewports at 6M. The hybrid path is the only design that *can* bypass per-Point typed-array reads for rows that have a source feature — whether it reliably *does* is an empirical question (the Answer records a mixed result), but no other design offers the avenue at all. Retaining `getClusters` means the encoded path remains available where the hybrid path doesn't win.
- **Why reuse the encoder/decoder for cluster rows?** Cluster rows are already computed during the lattice scan via `feature_at` (the same path `get_clusters` uses). Encoding them via `encode_results` and decoding via `decodeQueryResult` adds no new encode/decode surface — the cluster side is the existing path, restricted. A separate cluster-only encoder would duplicate `encode_results` for no gain.

## Considered Options

- **Hybrid (Point ids + Cluster encoded), two cluster buffers** — chosen. Render-complete in one call; zero-alloc Point rows; cluster side reuses the existing encoder/decoder verbatim. Ricky-approved layout (the ticket-10 design question). The drop-in `Feature[]` shape means callers swap `getClusters` → `getClustersIds` with no other change.
- **Pure ids (ticket-08 shape) + separate `getClusters` for clusters** — rejected. Two-call API doubles IPC tax on mixed viewports and is convoluted to use; Cluster rendering still needs the encoded path anyway.
- **Fully-encoded only (no `getClustersIds`)** — rejected. Leaves the decode-layer tax (the dominant Point-dense per-query cost per ticket 09) with no avenue to bypass it. The hybrid path's mixed measurement outcome doesn't retroactively make "no ids path" better — it makes "ship both, let callers pick" the right shape.
- **Hybrid with a single combined cluster buffer (rows+aggregated interleaved)** — rejected. Would require a new decode path diverging from `decodeQueryResult`; the two-buffer layout mirrors `getClusters` exactly and reuses the existing decoder with zero modification.

## Consequences

- The `getClustersIds` contract is `{ point_ids, cluster_rows, cluster_aggregated, count, specLen }` — five fields. `decodeHybridResult` reads `count` first and short-circuits on zero, but every field is always present (the empty shape surfaces all five) so the decode path never branches on field presence.
- Per-query buffer lifetime discipline is unchanged from ticket 07: `get_clusters_ids` allocates fresh `point_id_buf` / `row_buf` / `agg_buf` per call (no `Float64Array::view` aliasing UB across calls).
- The hybrid path requires the main thread to hold source features. `load_coords` callers (flat coordinate input, no source features) should use `getClusters`; `decodeHybridResult`'s defensive branch (missing source feature → null-geometry Feature) keeps it correct-but-suboptimal for that case.
- Oracle parity is membership-based (the `point_ids` set equals the encoded path's Point feature_ids for the same bbox/zoom — same lattice, same kd-tree `range` call), not byte-identical output. The WASM-boundary test asserts the cluster rows decode identically to the encoded path's cluster rows (same encoder, same `feature_at`).
